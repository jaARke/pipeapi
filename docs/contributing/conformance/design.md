# The runner's design

The conformance runner runs the case list against one connector at a time, starting and ending the backends and clients each case needs. This page says what the runner guarantees, why it's built this way, what it takes from comparable runners and what it leaves, and its limits. Why one runner drives an adapter per connector, rather than a suite per language, is the [adapter protocol's](../adapter-protocol.md#why-its-built-this-way) to say.

## What it guarantees

| To | The runner guarantees |
| --- | --- |
| A case | That it starts with processes of its own, and that everything it starts ends on every path out of it, so no case's failure reaches the next |
| A case | That every wait on another process is bounded by its hang guard and by the case's deadline, and names what it waited for when a bound passes, except as [Limits](#limits) says |
| A connector's author | That a fault of the runner or the adapter is never reported as the connector's behavior, and never passes as one of its expected failures, except as [Limits](#limits) says |
| A connector's author | That a case is skipped only for a reason it names: a component not built yet, with the issue that builds it, a transport or capability the adapter's hello doesn't declare, or, for a server case, a transport the raw client doesn't reach on the platform |
| The server's and the connectors' authors | That every reserved-route response and lease line the raw client receives is checked against the protocol's OpenAPI document, so a server that drifts from `protocol/` fails by name |
| Whoever runs it | That a process the run started that still runs at the run's end is killed, and fails the run |

## Why it's built this way

- **pytest, in the conformance project.** The runner is a pytest plugin beside the reference app, in the app's language: one place that starts and kills processes on the three OSes. pytest's parametrizing, skips, strict expected failures and reports serve the case list as they are, and each permutation is a parameter of one test, so pytest's own selection works on permutations.
- **Processes of its own for each case.** Each case starts its own backends and clients, and ends them before the next case starts; only the adapter's hello is read once for the run. A case's result then depends on nothing an earlier case left, such as a draining backend, a lease or a port, and its trace holds everything it did. It costs a backend's start for each case that needs one, a fraction of a second on a developer's machine.
- **A deadline for every case, and a named guard for every wait.** Each case has a deadline, longer for a case marked `slow`, set in `runner/case_run.py`. Every wait on another process takes the earlier of that deadline and its own hang guard, a named constant beside the wait with the reason for its value. A bound that passes on a wait for what the connector or the server does, such as a reply, an event or an observation, raises `DeadlinePassed`; on a wait the runner's own work needs, such as for an adapter's hello or a backend's start, it raises a fault of that work's own. A hung connector then fails its own case, and the next case runs.
  - Waits poll at a short interval rather than block, since a blocking wait on Windows takes no Ctrl+C until it ends.
  - A write to an adapter's stdin runs on a thread of its own, since a pipe the adapter stopped reading blocks a write once it's full, and a wait on the thread can be bounded where the write can't. A write that outlives its bound holds the stream until it fails, so the adapter is killed before its stdin closes, which ends the write.
- **Timing through observations.** A case waits for something it observes, never for time, as [Timing](cases.md#timing) says, so a case's result doesn't change with how loaded the machine is.
- **Gates kept apart.** A case doesn't run for one of three reasons, each with its own home and its own message:
  - It doesn't apply. To a platform or a transport, its definition says so, and the runner never collects it there. To a connector, the adapter's hello declares none of its transports or no capability it relies on, and the runner skips it as not applicable. A server case is skipped the same way on a transport the raw client doesn't reach, since the raw client declares the transports it reaches on each platform.
  - A component it needs isn't built. [`components.yaml`](../../../conformance/cases/components.yaml) says so, naming the issue that builds it, which flips it.
  - The connector is known to fail it, as the connector's [expected failures](adapters.md#expected-failures) say.

  A connector has no list of cases to skip: a case it can't pass yet is an expected failure, which fails the run once it passes, so no entry outlives its fix.
- **Faults apart from failures.** An expected failure covers only an assertion or a passed deadline, raised as the case runs. A fault of the runner or the adapter, which the adapter protocol's refusals, schema and framing tell apart, raises something else, so it fails a listed case all the same, and a broken adapter can't hide behind a connector's known failures. pytest applies an expected failure to a test's setup and teardown too, so an assertion or a wait that fails as the runner sets up or ends a case raises `RunnerFault` instead.
- **Invariants checked at each case's end.** Once a case's implementation passes, the runner ends its clients and runs each check `runner/invariants.py` holds, keyed by the invariant's ID in the case list, so a check sees everything the clients wrote. A violation is an assertion, the case's own failure, with a note that names the invariant. The invariants on schemas are checked as each line arrives instead, by the raw client and the adapter session, so their entries in `runner/invariants.py` check nothing more.
- **Invariants gated as cases are.** An invariant that needs a component, such as a check of what pipeapi's server does, names it in `needs`, and the runner checks it only once every component it needs is built. Each run holds a test for each invariant, skipped until then, which fails once they're all built while `runner/invariants.py` has no check for it, so the issue that builds an invariant's last component checks it, just as the one that builds a case's last component implements the case.
- **The contract checked where it's received.** The raw client checks each response against the protocol's OpenAPI document, driven by the document rather than by route, references followed: its status must be one the operation lists, each header its response defines must meet its definition, and its body, or each line of a stream, the schema of its media type, with each line ending in LF alone. A route the document gains is then checked with no code of its own.
- **A child's environment.** A case's changes to a child's environment, such as proxy variables, apply to the runner's own only while the child starts, through pytest's `MonkeyPatch`. The child then sees the runner's environment with exactly the case's changes, and an adapter also sees the runner's own environment's scripts directory first on PATH, as `uv run` puts it, so a run started by an editor runs what the recipes do. The runner's code reads no variable, as [the environment's rule](../python.md#the-environment) has it.
- **Traces kept.** Each run writes a directory of its own, named for when it started, its connector and the runner's PID, so two runs never share one. The runner never deletes one, since only the person who ran it knows which they still need.
- **Fixed operation IDs.** The reference app keeps its operation IDs fixed, as [its routes](reference-app.md#routes) say, so every adapter's generated client keeps its methods' names.

### Ending processes

- **A client is killed by its hello's PID, and only it.** The runner kills the process its hello names, hard, never its process group, its process tree or a job object, so the backends it spawned keep running, as the cases of a killed client need. On Windows the process the runner started may be a virtual environment's launcher, which exits on its own once the program does; killing the launcher first would end its job object and every process in it.
  - The hello's PID must be the process the runner started or a descendant of it, as psutil shows at the hello, so a wrong PID, such as the runner's own, is an adapter fault rather than a process the runner kills. The runner keeps psutil's handle of it, which refuses a PID the OS has given another process since.
  - A process the runner started that still runs past a hang guard once its program has ended, such as a wrapper that outlives what it runs, is killed too, and so is one whose program ended before it.
- **What a case started ends with it.** Every process the case started is killed on every path out of the case, and waited for within a hang guard; one that outlives its kill fails the case. Ending one process carries on past another's failure, and the failure names each.
- **What a case learned of ends with it too.** The backends a connector spawned, which the runner didn't start, are ended by the PIDs their observation logs give, on every path out of the case. Each is killed only while psutil shows that its environment names that log in `REFERENCE_APP_LOG`, so a PID the OS has given another process since is left alone. A process whose environment psutil can't read may still be the case's, so it fails the case as one that outlived its kill.
- **The run checks its end.** A process the run started that still runs once the run ends is killed, and fails the run, naming each.

## Prior art

| Prior art | Taken | Left |
| --- | --- | --- |
| [Protocol Buffers' conformance runner](https://github.com/protocolbuffers/protobuf/tree/main/conformance) | A strict failure list, where a listed test that passes fails the run, and so does an entry that matches no test; a testee that times out told apart from one that ends its output early; a testee killed hard when it doesn't exit in time, with the wait for it bounded too | One testee for the whole run, spawned again after a failure, since each case here starts processes of its own; and signalling the testee's process group, since a killed client's backends must keep running |
| [Connect RPC's conformance runner](https://github.com/connectrpc/conformance/blob/main/docs/configuring_and_running_tests.md) | Known failures that fail the run once they pass, since the list is then stale; a failure reported by the permutation's full name, with what was observed; the features an implementation declares deciding which cases apply to it | Known-flaky cases, which may fail without failing the run, since a case here waits on observations rather than time, so a flaky case is a bug in the case; and skipping a case whose crash or deadlock keeps the run from completing, since here a case's deadline and its own processes confine such a bug to its case |
| [Datadog's system-tests](https://github.com/DataDog/system-tests) | Processes of their own for each test, as its parametric tests get containers of their own; logs kept in a directory of their own, here one per run; every payload checked against a schema, with a violation named by where it is | A list of known schema violations kept apart from the tests' own, since here a contract violation fails its case, which the connector's one list of expected failures covers |

## Limits

- **The raw client bounds each phase of a request, not the whole.** httpx2 applies a request's timeout to connecting, to each read and to each write, so a server that keeps sending slowly holds a raw-client request past the case's deadline.
- **A hung adapter looks like a hung connector.** An adapter whose own command loop hangs writes no reply, just as one whose connector's call hangs writes none, so the wait for the reply raises `DeadlinePassed`, which an expected failure covers, since the protocol can't tell the two apart.
- **`invariant.event-order` sees only what an adapter wrote by its end.** An outage still open when a client ends passes, since an adapter exits at the end of its stdin without waiting for one to end, and so does an event an adapter wrote between a `close` command and its reply, since only the reply shows that `close()` came first.
- **A client's stdout is read to its end only within a hang guard.** Once a client has ended, the runner reads its stdout until the pipe ends, so the invariants see every line it wrote. A process the client started may hold the pipe open, such as one that inherited it, so the runner waits only within a hang guard, records in the trace that it passed, and goes on with the lines it read.
- **A runner killed hard ends nothing.** No process is tied to the runner, on purpose, so a runner killed hard, rather than interrupted, leaves what it started running. The traces name each process's PID.
- **A backend's port is chosen, then bound.** The runner picks a free loopback port and releases it for uvicorn to bind, so another process can take it in between. The backend's start then fails by name, rather than the case reaching another process: uvicorn fails to bind, or the PID that `/seen` reports isn't the one the `startup` record gives.
