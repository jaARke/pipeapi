## connect()

`connect()` takes the [options](/pipeapi/reference/connector-api/options/), each of them optional, and its language's own cancellation signal, such as an `AbortSignal` or a `CancellationToken`. It checks its options as [validation](/pipeapi/reference/connector-api/options/#validation) says, then runs the [connect sequence](/pipeapi/reference/protocol-v1/connecting/#connect-sequence):

- **Endpoint.** It expands the templates of an endpoint it is given. Given none, it generates an endpoint whose transport is <Cite name="transport" connectorApi="options" />, as [generated endpoints](/pipeapi/reference/protocol-v1/endpoints/#generated-endpoints) says, with a token, and for loopback with a rendezvous file.
- **Attach or spawn.** Given a loopback endpoint whose port is 0, which only another client generates, it attaches without spawning, and waits for the rendezvous file and the hello as the client that generated the endpoint does. With an endpoint it generated, it spawns the backend. Given any other endpoint, it tries once to connect to it, waiting only for a busy pipe, as [opening connections](/pipeapi/reference/connector-api/lease-loss-and-outages/#opening-connections) says, and attaches when something accepts the connection. When nothing does, because the connection is refused or there is no such pipe or socket, it spawns the backend when it has a <Cite name="command" connectorApi="options" />, and otherwise fails with <Cite name="backend_unavailable" connectorApi="errors" />.
- **Hello.** It sends the hello again <Cite name="hello_poll_initial" connectorApi="constants" /> after a failed attempt, doubling the wait after each one up to <Cite name="hello_poll_maximum" connectorApi="constants" />, and on loopback with a rendezvous file, it reads the file again before each one. While a process it spawned runs, it keeps trying. When that process exits with <Cite name="already_running" section="exit_codes" version="v1" />, because another server took the endpoint in a [spawn race](/pipeapi/reference/protocol-v1/connecting/#spawn-race), or exits after answering <Cite name="draining" section="rejections" version="v1" />, it goes on as a client that has spawned nothing; when it exits any other way before the backend is ready, `connect()` fails with <Cite name="startup_failed" connectorApi="errors" />. A client that has spawned nothing goes back to attach or spawn whenever a hello's connection finds nothing accepting, so it spawns again where the bullet above says it may, and without a command fails with <Cite name="backend_unavailable" connectorApi="errors" />.
- **Rejections.** A hello or a lease request answered with <Cite name="draining" section="rejections" version="v1" /> counts as no answer, so it keeps trying for the hello, as the bullet above says. Any other rejection of the hello fails it with <Cite name="verification_failed" connectorApi="errors" />, since the server isn't one it can verify. A lease request rejected with <Cite name="enrollment_failed" section="rejections" version="v1" /> after a verified hello, such as for a challenge that expired or that the server evicted, makes it try for a fresh hello and enroll again, once, and a second such rejection fails it with <Cite name="protocol_error" connectorApi="errors" />. A lease request rejected with <Cite name="unsupported_protocol" section="rejections" version="v1" /> fails it with <Cite name="protocol_error" connectorApi="errors" />, since the server contradicted its own hello.
- **Verification.** A hello answered with a response that holds no valid hello, such as the 404 of an HTTP server that isn't pipeapi, or whose proof doesn't check out, or whose PID doesn't match the connection's where its language's runtime can read that PID, fails it with <Cite name="verification_failed" connectorApi="errors" />, and it never enrolls with that server. On loopback with a rendezvous file, which may still name a port another server has since taken, it instead reads the file again and keeps trying for the hello.
- **Deadline.** <Cite name="connectTimeout" connectorApi="options" /> bounds the whole sequence, and when it passes before the backend is ready, `connect()` fails with <Cite name="connect_timeout" connectorApi="errors" />. When the app cancels it, it fails with its language's own cancellation error.
- **Cleanup.** When it fails after spawning a backend on an endpoint it generated, it kills that process and, once the process has exited, removes the directory it generated, all before it returns the error, since no other client can reach that backend. It kills the process rather than asking it to stop, since no client has used it, and one still starting, such as in its app's lifespan startup, may never act on a request to stop. A backend spawned on an endpoint the app gave stops on its own after its [startup grace](/pipeapi/reference/protocol-v1/lifetime/#graces), unless another client has enrolled.

## The Backend

Each `connect()` returns a `Backend` of its own, with its own endpoint, token, lease, connections and primitive. Nothing is shared between `Backend`s or held globally, so an app may use any number of backends at once, each with its own schema and generated client, and one backend failing leaves the others alone.

- `clientId` is the client ID of the current lease, which changes whenever the connector opens a new one.
- `close()` releases the lease and closes the connections, and never waits for the backend to exit. It ends a reconnect or a respawn at once, and no lifecycle event follows it. Requests waiting for ready then fail with <Cite name="closed" connectorApi="errors" />, as does every later call on the `Backend`.
- A connector never ties a spawned backend's life to its own process, such as with a job object that ends the backend when the connector's process exits, or Linux's parent-death signal: a backend runs while any client holds a lease, as protocol v1's [leases](/pipeapi/reference/protocol-v1/leases/) say, so another client's lease keeps it running after the process that spawned it ends.
- The backend stops once no client holds a lease and its [idle grace](/pipeapi/reference/protocol-v1/lifetime/#graces) passes. Until then, a backend on an endpoint the connector generated is reachable only by clients given that endpoint. The connector removes the directory it generated once it sees the backend exit, while its own process still runs; otherwise the directory stays, as [generated files](/pipeapi/reference/protocol-v1/lifetime/#generated-files) says.
- `shutdown()` requests <Cite name="/__pipeapi/shutdown" version="v1" />, which [stops](/pipeapi/reference/protocol-v1/lifetime/#stopping) the backend whatever leases other clients hold. Its own lease then ends as every client's does, and the `Backend` is [lost](/pipeapi/reference/connector-api/lease-loss-and-outages/#lease-loss).
