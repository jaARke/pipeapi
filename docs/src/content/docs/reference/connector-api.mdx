A connector is pipeapi's client library for one language: Node, .NET, Rust, Go or Python. It implements [protocol v1](/pipeapi/reference/protocol-v1/) for an app, and every connector offers the same capabilities, options, events and errors, each in its language's idiom. This page states that shared surface. Each connector's API reference maps its own names onto it, and the conformance suite ([#5](https://github.com/jaARke/pipeapi/issues/5)) holds every connector to it.

## Conventions

Key words in capitals, such as MUST and SHOULD, mean what [protocol v1's conventions](/pipeapi/reference/protocol-v1/#conventions) say, and this page uses the [terms](/pipeapi/reference/protocol-v1/#terms) protocol v1 defines. The **app** is the program that uses a connector, and a **`Backend`** is the object through which it uses one backend.

The file <ContractLink path="protocol/connector-api/connector-api.schema.json" /> is part of this page. It is a JSON Schema whose definitions hold the options, the lifecycle events, the errors and the log records, as JSON can carry them, and the fixed values every connector uses. The tables on this page render it, and every option, request option, lifecycle event, error, reason for a lost `Backend`, log event and constant this page names comes from it, as do the fields of events, errors and log records in its tables. The conformance suite's adapters and each connector's tests read it too.

### Names in each language

The file spells each name once. Options, and the fields of events, errors and log records, are in camelCase there, and each language spells them by its own conventions: <Cite name="envPrefix" connectorApi="options" /> stays as it is in Node, and becomes `EnvPrefix` in .NET and Go, and `env_prefix` in Rust and Python. The capabilities below follow the same rule.

Event types, error codes and log events are snake_case strings that apps match on. A connector carries each one as a string spelled exactly as the file spells it. A language that also names one as a member, such as a .NET event or an enumeration's case, spells that member by its own conventions.

Durations are seconds in the file, and each language takes them in its own form, such as a `TimeSpan` in .NET or a `time.Duration` in Go. Each connector's issue settles its language's forms: [#7](https://github.com/jaARke/pipeapi/issues/7) for Node, [#15](https://github.com/jaARke/pipeapi/issues/15) for .NET, [#16](https://github.com/jaARke/pipeapi/issues/16) for Rust, [#17](https://github.com/jaARke/pipeapi/issues/17) for Go and [#18](https://github.com/jaARke/pipeapi/issues/18) for Python.

## Capabilities

| Capability | What it does |
| --- | --- |
| `connect(options)` | The single entry point. It runs the [connect sequence](/pipeapi/reference/protocol-v1/#connect-sequence), attaching to a backend at the endpoint or spawning one, and returns a `Backend`. |
| `backend.close()` | Releases this client's lease and connections. The backend stops only once no client holds a lease. |
| `backend.shutdown()` | Stops the backend for every client. |
| Untyped request | Sends one HTTP request over the endpoint's transport, with the headers every request carries. |
| HTTP primitive | The language's standard HTTP client object, set up for this backend, for generated clients to use. |
| `dial()` | Opens a raw connection to the endpoint, for an HTTP client the primitive doesn't cover, with the headers its caller adds to each request. |
| SSE helper | Iterates the server-sent events of a streaming response. |
| `ValidationError` | Turns the app's 422 validation error into a structured error. |
| `backend.clientId` | The client ID of the current lease. |
| Lifecycle events | The [events](#lifecycle-events) a `Backend` emits as its lease and its backend change. |
| Outage handling | [Built into](#lease-loss-and-outages) the untyped request and the primitive: a request not yet sent waits for the backend to be ready, a request in flight is sent again only when that is safe, and the SSE helper resumes a stream. |
| Busy-pipe retry | On Windows, a connection that finds every instance of the pipe busy [tries again](#opening-connections) until <Cite name="connectTimeout" connectorApi="options" /> passes, for every connection the connector opens. |
| Respawn | When the app turns it on, the connector that spawned a backend [starts it again](#respawn) after it exits unexpectedly. |

### connect()

`connect()` takes the [options](#options), each of them optional, and its language's own cancellation signal, such as an `AbortSignal` or a `CancellationToken`. It checks its options as [validation](#validation) says, then runs the [connect sequence](/pipeapi/reference/protocol-v1/#connect-sequence):

- **Endpoint.** It expands the templates of an endpoint it is given. Given none, it generates an endpoint whose transport is <Cite name="transport" connectorApi="options" />, as [generated endpoints](/pipeapi/reference/protocol-v1/#generated-endpoints) says, with a token, and for loopback with a rendezvous file.
- **Attach or spawn.** Given a loopback endpoint whose port is 0, which only another client generates, it attaches without spawning, and waits for the rendezvous file and the hello as the client that generated the endpoint does. With an endpoint it generated, it spawns the backend. Given any other endpoint, it tries once to connect to it, waiting only for a busy pipe, as [opening connections](#opening-connections) says, and attaches when something accepts the connection. When nothing does, because the connection is refused or there is no such pipe or socket, it spawns the backend when it has a <Cite name="command" connectorApi="options" />, and otherwise fails with <Cite name="backend_unavailable" connectorApi="errors" />.
- **Hello.** It sends the hello again <Cite name="hello_poll_initial" connectorApi="constants" /> after a failed attempt, doubling the wait after each one up to <Cite name="hello_poll_maximum" connectorApi="constants" />, and on loopback with a rendezvous file, it reads the file again before each one. While a process it spawned runs, it keeps trying. When that process exits with <Cite name="already_running" section="exit_codes" version="v1" />, because another server took the endpoint in a [spawn race](/pipeapi/reference/protocol-v1/#spawn-race), or exits after answering <Cite name="draining" section="rejections" version="v1" />, it goes on as a client that has spawned nothing; when it exits any other way before the backend is ready, `connect()` fails with <Cite name="startup_failed" connectorApi="errors" />. A client that has spawned nothing goes back to attach or spawn whenever a hello's connection finds nothing accepting, so it spawns again where the bullet above says it may, and without a command fails with <Cite name="backend_unavailable" connectorApi="errors" />.
- **Rejections.** A hello or a lease request answered with <Cite name="draining" section="rejections" version="v1" /> counts as no answer, so it keeps trying for the hello, as the bullet above says. Any other rejection of the hello fails it with <Cite name="verification_failed" connectorApi="errors" />, since the server isn't one it can verify. A lease request rejected with <Cite name="enrollment_failed" section="rejections" version="v1" /> after a verified hello, such as for a challenge that expired or that the server evicted, makes it try for a fresh hello and enroll again, once, and a second such rejection fails it with <Cite name="protocol_error" connectorApi="errors" />. A lease request rejected with <Cite name="unsupported_protocol" section="rejections" version="v1" /> fails it with <Cite name="protocol_error" connectorApi="errors" />, since the server contradicted its own hello.
- **Verification.** A hello whose proof doesn't check out, or whose PID doesn't match the connection's where its language's runtime can read that PID, fails it with <Cite name="verification_failed" connectorApi="errors" />, and it never enrolls with that server. On loopback with a rendezvous file, which may still name a port another server has since taken, it instead reads the file again and keeps trying for the hello.
- **Deadline.** <Cite name="connectTimeout" connectorApi="options" /> bounds the whole sequence, and when it passes before the backend is ready, `connect()` fails with <Cite name="connect_timeout" connectorApi="errors" />. When the app cancels it, it fails with its language's own cancellation error.
- **Cleanup.** When it fails after spawning a backend on an endpoint it generated, it stops that process before it returns the error, since no other client can reach it, and removes the directory it generated once the process has exited. A backend spawned on an endpoint the app gave stops on its own after its [startup grace](/pipeapi/reference/protocol-v1/#graces), unless another client has enrolled.

### The Backend

Each `connect()` returns a `Backend` of its own, with its own endpoint, token, lease, connections and primitive. Nothing is shared between `Backend`s or held globally, so an app may use any number of backends at once, each with its own schema and generated client, and one backend failing leaves the others alone.

- `clientId` is the client ID of the current lease, which changes whenever the connector opens a new one.
- `close()` releases the lease and closes the connections, and never waits for the backend to exit. It ends a reconnect or a respawn at once, and no lifecycle event follows it. Requests waiting for ready then fail with <Cite name="closed" connectorApi="errors" />, as does every later call on the `Backend`.
- The backend stops once no client holds a lease and its [idle grace](/pipeapi/reference/protocol-v1/#graces) passes. Until then, a backend on an endpoint the connector generated is reachable only by clients given that endpoint. The connector removes the directory it generated once it sees the backend exit, while its own process still runs; otherwise the directory stays, as [generated files](/pipeapi/reference/protocol-v1/#generated-files) says.
- `shutdown()` requests <Cite name="/__pipeapi/shutdown" version="v1" />, which [stops](/pipeapi/reference/protocol-v1/#stopping) the backend whatever leases other clients hold. Its own lease then ends as every client's does, and the `Backend` is [lost](#lease-loss).

### Requests

The untyped request and the primitive add these headers to every request, with the values of the current lease: Host, whose value is <Cite name="host" section="constants" version="v1" />, <Cite name="X-PipeAPI-Protocol" version="v1" /> and <Cite name="X-PipeAPI-Session" version="v1" />. The primitive carries them itself, so a generated client needs to know nothing about pipeapi; its base URL is `http://` followed by the Host value. Both return every response the app sends, whatever its status: an HTTP status is never a connector's error.

| Language | Untyped request and primitive | Typed client |
| --- | --- | --- |
| Node ([#7](https://github.com/jaARke/pipeapi/issues/7)) | `backend.fetch()`, with the signature of the WHATWG `fetch`, and `backend.clientOptions`, which holds the base URL and that `fetch`, the two options nearly every TypeScript client takes | openapi-fetch |
| .NET ([#15](https://github.com/jaARke/pipeapi/issues/15)) | An `HttpMessageHandler` to build an `HttpClient` on | NSwag, Kiota or Refit |
| Rust ([#16](https://github.com/jaARke/pipeapi/issues/16)) | A `reqwest::Client` | progenitor |
| Go ([#17](https://github.com/jaARke/pipeapi/issues/17)) | An `*http.Client` | oapi-codegen |
| Python ([#18](https://github.com/jaARke/pipeapi/issues/18)) | An `httpx.Client` or `httpx.AsyncClient` | openapi-python-client |

Each connector's issue settles the names, and the untyped request where the table gives none.

### dial()

`dial()` opens a raw connection to the endpoint, as a stream in its language's form, for an HTTP client the primitive doesn't cover or a protocol that takes over an upgraded connection. On a named pipe, it retries a busy pipe as every connection does.

Nothing on the connection is pipeapi's: its caller MUST add to every request the headers the untyped request adds, Host, <Cite name="X-PipeAPI-Protocol" version="v1" /> and <Cite name="X-PipeAPI-Session" version="v1" />, and the `Backend` exposes their current values for it. The token never goes on the connection, since the session stands in for it. A request on a dialed connection gets none of the connector's outage handling. When the connector opens a new lease, a request with the old session gets <Cite name="invalid_session" section="rejections" version="v1" />, and the caller reads the current values and sends it again.

### SSE helper

The SSE helper takes a response whose content type is `text/event-stream`, from the untyped request or the primitive, and iterates its events as the [HTML standard](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream) parses them, each with its type, its data and its ID.

### ValidationError

FastAPI answers a request that fails validation with a 422 whose body's `detail` lists each failure. `ValidationError` turns such a response into the error <Cite name="validation_error" connectorApi="errors" />, which holds each failure's location, message and type, and leaves a response with any other status or body as it is. Each connector's issue settles its form, such as a function that takes a response.

### Transports and proxies

An endpoint's scheme picks its transport, as [endpoint URLs](/pipeapi/reference/protocol-v1/#endpoint-urls) says.

- A connector rejects an endpoint whose transport its OS lacks with <Cite name="unsupported_transport" connectorApi="errors" /> when `connect()` runs, never when the app imports or compiles it. Code for one platform's transport is built only into that platform's build, and other platforms get a stub that fails with that error.
- Every connector turns proxies off on its primitive, as [host and proxies](/pipeapi/reference/protocol-v1/#host-and-proxies) requires, explicitly, since each language's default differs.
- When an optional native piece is missing, such as a Node addon on an unsupported CPU, the connector logs <Cite name="native_unavailable" connectorApi="log_events" /> and treats the feature that needs it as unavailable. Whether `connect()` then proceeds without checking the server's PID is [#8](https://github.com/jaARke/pipeapi/issues/8)'s to settle.
- Node's standard library can neither read the PID of the process at the other end of a named pipe or a Unix domain socket, which the connect sequence's verification checks where a client can, nor open a named pipe at identification-level impersonation, which [transport access](/pipeapi/reference/protocol-v1/#transport-access) asks for. Whether the Node connector ([#7](https://github.com/jaARke/pipeapi/issues/7)) takes a native piece for both is [#8](https://github.com/jaARke/pipeapi/issues/8)'s to settle.

| Language | Pipes and sockets | Loopback | Proxies off |
| --- | --- | --- | --- |
| Node | `http.request` with `socketPath`, which takes a socket's path or a pipe's | Node's TCP transport | An `http.Agent` of its own on every request, never the global one |
| .NET | `SocketsHttpHandler.ConnectCallback`, returning a `NamedPipeClientStream` or a `Socket` on a `UnixDomainSocketEndPoint` | The handler's TCP transport | `UseProxy = false` on the handler, which otherwise uses the Windows system proxy |
| Rust | reqwest's `ClientBuilder::unix_socket` and `windows_named_pipe` | reqwest's TCP transport | `.no_proxy()` on the `ClientBuilder` |
| Go | An `http.Transport` whose `DialContext` dials `unix`, or go-winio's `DialPipeContext` | The standard TCP dialer | `Proxy: nil` on the `http.Transport`, whose default reads proxy environment variables |
| Python | httpx's `uds` transport on POSIX, and on Windows an httpcore network backend that opens the pipe | httpx's TCP transport | `trust_env=False` on the httpx client |

### Environment

The options with an environment variable in the table are read from the client's environment too. A connector reads its environment once, as `connect()` starts, and takes each option's value from the first of these that gives one:

1. The option, as the app passes it.
2. Its environment variable. A variable set to the empty string counts as unset.
3. Its default, or what its description says happens when it is unset.

With <Cite name="envPrefix" connectorApi="options" /> set, a connector reads each variable under a name made of the prefix, an underscore, and the variable's own name: with the prefix `WORKER`, it reads `WORKER_` followed by <Cite name="PIPEAPI_ENDPOINT" version="v1" />, and so on for every variable in the table, <Cite name="PIPEAPI_RENDEZVOUS" version="v1" /> included. It then never reads the unprefixed names, which belong to the backend whose clients use no prefix. A library that embeds a connector SHOULD set a prefix of its own, so that the variables an app sets for its own backend don't reach the library's.

A value from the environment is checked as the option's value is, in the form the protocol's [environment variables](/pipeapi/reference/protocol-v1/#environment-variables) give it, such as whole seconds or `never` for a grace. A malformed one fails as the option would, and the error's message names the variable.

### What a spawned backend receives

The options <Cite name="startupGrace" connectorApi="options" />, <Cite name="idleGrace" connectorApi="options" /> and <Cite name="leaseTtl" connectorApi="options" /> apply only to a backend the connector spawns: a backend that is already running keeps its own. A spawned backend's environment is the client's own, with <Cite name="env" connectorApi="options" /> set over it, and then:

1. The connector removes every variable named as the protocol names its [environment variables](/pipeapi/reference/protocol-v1/#environment-variables), whether alone or after a prefix and an underscore, comparing names without regard to case on every OS.
2. It sets <Cite name="PIPEAPI_ENDPOINT" version="v1" /> and <Cite name="PIPEAPI_TOKEN" version="v1" />, <Cite name="PIPEAPI_RENDEZVOUS" version="v1" /> when the endpoint is loopback with a generated port, and the variable of each grace and TTL option that has a value, each under its unprefixed name, as protocol v1 requires.

So a backend never inherits the settings meant for another backend, or a token under a prefix, which the server wouldn't remove from its environment.

### Validation

A connector checks every option before it spawns a backend or connects:

- An endpoint that breaks the rules for [endpoint URLs](/pipeapi/reference/protocol-v1/#endpoint-urls) or [templates](/pipeapi/reference/protocol-v1/#templates) fails with <Cite name="invalid_endpoint" connectorApi="errors" />, on every OS, and so does a loopback endpoint whose port is 0 given without its <Cite name="rendezvous" connectorApi="options" />.
- A valid endpoint whose transport the OS lacks fails with <Cite name="unsupported_transport" connectorApi="errors" />, and so does a <Cite name="transport" connectorApi="options" /> the OS lacks.
- Any other value that the table's type or description doesn't allow fails with <Cite name="invalid_option" connectorApi="errors" />. That includes:
  - an endpoint given without a <Cite name="token" connectorApi="options" />, since a connector generates a token only with the endpoint it generates;
  - an empty token;
  - an <Cite name="idleGrace" connectorApi="options" /> of `never` for an endpoint the connector generates, since that backend would outlive every client that can reach it unless one was given the endpoint;
  - a lease TTL below <Cite name="lease_ttl_minimum" section="durations" version="v1" />;
  - a variable in <Cite name="env" connectorApi="options" /> that the connector would remove from a spawned backend's environment.

## Lease loss and outages

A connector holds its lease from `connect()` until `close()`, and handles the outages that end it, so that the app's requests and the typed client it built keep working while a backend restarts. Requests that don't go through the untyped request or the primitive, such as those over `dial()`, get none of this.

### Holding the lease

- A connector concludes that its lease is lost only when the lease stream ends, as [heartbeats](/pipeapi/reference/protocol-v1/#heartbeats) and [lease loss](/pipeapi/reference/protocol-v1/#lease-loss) say. Heartbeats that stop, a renewal that fails and a request that is rejected never end it.
- A connector sets no read timeout on the lease request, whatever its HTTP library's default, since heartbeats stop while a backend is paused, such as in a debugger.
- When the session event gives a TTL, the connector renews its lease at least as often as [lease TTL](/pipeapi/reference/protocol-v1/#lease-ttl) asks, requesting <Cite name="/__pipeapi/renew" version="v1" /> when no other request has carried its session in that time. A renewal that fails logs <Cite name="renewal_failed" connectorApi="log_events" />, and the connector renews again at the next interval.
- When its lease ends, the connector closes the primitive's idle connections, so no later request goes out on a connection to the backend that ended it.

### Lease loss

When its lease stream ends, a connector acts on the [end reason](/pipeapi/reference/protocol-v1/#lease-end-reasons):

| The lease ended | The connector |
| --- | --- |
| With <Cite name="shutdown" section="lease_end_reasons" version="v1" /> | Emits <Cite name="lost" connectorApi="events" /> with the reason <Cite name="shutdown" connectorApi="lost_reasons" /> |
| With <Cite name="revoked" section="lease_end_reasons" version="v1" /> | Emits <Cite name="lost" connectorApi="events" /> with the reason <Cite name="revoked" connectorApi="lost_reasons" /> |
| With <Cite name="restart" section="lease_end_reasons" version="v1" />, <Cite name="expired" section="lease_end_reasons" version="v1" /> or a reason it doesn't know, or without an end event | Emits <Cite name="reconnecting" connectorApi="events" /> with the reason, or null without one, then [reconnects](#reconnecting) |

- A connector that spawned the backend reads the lease stream to its end before it acts on the backend's exit, so a backend that sent an end event is handled by that event's reason. When the backend exits while the lease is still open, the exit ends the lease without an end event.
- Every <Cite name="reconnecting" connectorApi="events" /> is followed by exactly one of <Cite name="reconnected" connectorApi="events" />, <Cite name="respawned" connectorApi="events" /> or <Cite name="lost" connectorApi="events" />, unless the app calls `close()` first, and the connector emits no other event in between.

### Reconnecting

To reconnect, a connector runs the [connect sequence](/pipeapi/reference/protocol-v1/#connect-sequence) again as [`connect()`](#connect) does, as a new client, with these differences:

- It uses the endpoint, the token and the rendezvous file it resolved when `connect()` ran, so it never reads its environment again or generates new ones.
- It never spawns a backend, except to [respawn](#respawn) one, and it doesn't fail when nothing accepts its connection, as a client without a command would in `connect()`. It keeps trying for the hello instead, until a backend is ready or <Cite name="reconnectBudget" connectorApi="options" /> has passed since the lease ended.
- A hello or a lease request answered with <Cite name="draining" section="rejections" version="v1" /> counts as no answer, so it keeps trying for the hello within the budget.
- It negotiates a protocol version and verifies the server again, and treats every other rejection as `connect()` does.
- Once it holds a new lease, it emits <Cite name="reconnected" connectorApi="events" /> with the old and new client IDs, and `clientId` gives the new one.
- When the budget passes, or the sequence fails with an error, such as <Cite name="verification_failed" connectorApi="errors" />, it emits <Cite name="lost" connectorApi="events" /> with the reason <Cite name="unavailable" connectorApi="lost_reasons" /> and that error's code, which is <Cite name="connect_timeout" connectorApi="errors" /> when the budget passed.
- When it spawned the backend and sees the backend exit, it stops waiting for one: it respawns the backend when respawn applies, and otherwise emits <Cite name="lost" connectorApi="events" /> with the reason <Cite name="exited" connectorApi="lost_reasons" />, the exit's status or signal, and the stderr tail.

### Lost

The <Cite name="lost" connectorApi="events" /> event is terminal:

- A connector never reconnects or respawns a `Backend` that is lost, and emits no event after it.
- Every request waiting for ready, and every request after the event, fails at once with <Cite name="backend_unavailable" connectorApi="errors" />, and so does `dial()`. A request the connector had already written finishes or fails on its own connection, with <Cite name="request_interrupted" connectorApi="errors" /> when that connection drops.
- A connector that generated the endpoint removes the directory it generated once it sees its backend exit, since it won't start another backend for that endpoint. `close()` still releases what the `Backend` holds.
- To use a backend again, the app calls `connect()` again, which returns a new `Backend`, and builds its typed client on that `Backend`'s primitive.

### Addresses

A connector resolves a `Backend`'s address as it opens each connection, so every connection the untyped request, the primitive or `dial()` opens goes to the backend that serves the `Backend` now. On loopback with a rendezvous file, the connector reads the file again before each hello it sends, as [rendezvous file](/pipeapi/reference/protocol-v1/#rendezvous-file) requires, since a backend that starts again binds another port. A `Backend`'s endpoint and token never change, so its primitive, and the typed client the app built on it, keep working across a reconnect or a respawn.

### Opening connections

- In `connect()`, the first connection to an endpoint the app gave is a single attempt, as [`connect()`](#connect) says, which waits only for a busy pipe. The hellos after it try again until <Cite name="connectTimeout" connectorApi="options" /> passes.
- After `connect()`, every connection a `Backend` opens, for its lease, a request or `dial()`, tries again when it fails to connect, until <Cite name="connectTimeout" connectorApi="options" /> has passed since its first attempt.
- On Windows, a connection that finds every instance of the named pipe busy waits for one to free up, logging <Cite name="pipe_busy" connectorApi="log_events" /> for each attempt, and stops waiting when <Cite name="connectTimeout" connectorApi="options" /> passes, however long its language's runtime would wait on its own, as Node's libuv does in its calls to `WaitNamedPipeW`.
- A request whose connection can't be opened in that time fails with <Cite name="backend_unavailable" connectorApi="errors" />, and so does `dial()`. While the `Backend` is reconnecting, a request [waits for ready](#waiting-for-ready) instead.

### Waiting for ready

A request through the untyped request or the primitive is unsent until the connector writes some of it to a connection. While the `Backend` is reconnecting, an unsent request:

- waits, and goes out with the new lease's session once the connector holds one;
- fails at once with <Cite name="backend_unavailable" connectorApi="errors" /> when the `Backend` is lost, with <Cite name="closed" connectorApi="errors" /> when the app closes it, and with its language's own error when its own timeout or cancellation comes first;
- fails at once with <Cite name="backend_unavailable" connectorApi="errors" /> instead of waiting, when its <Cite name="waitForReady" connectorApi="request_options" /> is false.

Waiting never sends a request twice, since the request hasn't left the client before it goes out.

### Safe retry

A request is in flight from the moment the connector writes some of it until its response arrives in full. When its connection drops while it is in flight:

- Before the response's headers arrive, the connector sends the request again, once, with the session of its current lease, waiting for ready first when it is reconnecting, when all of these hold:
  - its <Cite name="safeRetry" connectorApi="request_options" /> isn't false;
  - its method is `GET`, `HEAD` or `OPTIONS`, or it carries an `Idempotency-Key` header;
  - the connector can send its body again, which it can't for a stream it didn't keep.
- A request it sends again logs <Cite name="request_retried" connectorApi="log_events" />. Any other request in flight, or one sent again whose connection drops too, fails with <Cite name="request_interrupted" connectorApi="errors" />.
- After the response's headers arrive, the connector never sends the request again, and reading the rest of the response fails with <Cite name="request_interrupted" connectorApi="errors" />.

`PUT` and `DELETE` are idempotent by HTTP's definition, but an app doesn't always implement them so, so they need an `Idempotency-Key` too, as with Go's `http.Transport`.

### Rejected requests

A response that carries <Cite name="X-PipeAPI-Rejected" version="v1" /> never reached the app, whatever its [rejection code](/pipeapi/reference/protocol-v1/#rejections), so sending the request again is safe whatever its method.

- The connector sends a rejected request again when all of these hold: the code is <Cite name="invalid_session" section="rejections" version="v1" /> or <Cite name="unsupported_protocol" section="rejections" version="v1" />, as it is for a request whose lease has ended; the request's <Cite name="safeRetry" connectorApi="request_options" /> isn't false; and the connector can send its body again. It waits for ready until it holds a lease other than the one whose credentials the request carried, for at most <Cite name="reconnectBudget" connectorApi="options" />, then sends the request again, once, with that lease's credentials.
- Otherwise, or when the budget passes first, the connector returns the rejection to the app as the response.

### Server-sent events

When the connection of a stream the SSE helper is iterating drops before the server ends the stream, the helper resumes it:

- It sends the stream's request again once the connector holds a lease, with `Last-Event-ID` set to the ID of the last event it received, as a browser's `EventSource` does. Before that, it waits for the reconnection time the stream last set with a `retry` field, or <Cite name="sse_retry_default" connectorApi="constants" /> when the stream set none.
- It resumes a stream only when the stream's request is a `GET` whose <Cite name="safeRetry" connectorApi="request_options" /> isn't false, and only once it has received an event with an ID, so a stream is never replayed from its start without the app knowing. Otherwise, the iteration fails with <Cite name="request_interrupted" connectorApi="errors" />.
- A stream it resumed that drops again before it delivers an event fails the iteration with <Cite name="request_interrupted" connectorApi="errors" />, so resuming never loops.
- It resumes a stream each time it drops after delivering an event, until the `Backend` is lost, when the iteration fails with <Cite name="backend_unavailable" connectorApi="errors" />.
- A stream the server ends ends the iteration.

An app that wants its streams to survive an outage gives their events IDs. A WebSocket, by contrast, is never resumed, as [WebSockets](#websockets) says.

## Respawn

A connector can start its backend again after it exits unexpectedly. Respawn is off unless the app sets <Cite name="respawn" connectorApi="options" />, since a backend that starts again has lost the app's in-memory state. It needs nothing from the protocol beyond what the connect sequence already does.

### When a connector respawns

A connector respawns a backend only when all of these hold:

- its <Cite name="respawn" connectorApi="options" /> is true;
- its `Backend` spawned the process that exited, in `connect()` or in an earlier respawn, so it saw the exit itself. A client that attached never respawns, since it can't see the backend's exit;
- the process exited unexpectedly: with a status other than 0, or by a signal.

A backend that stops normally, after a shutdown request, a signal it handles or a grace, sends an end event with the reason <Cite name="shutdown" section="lease_end_reasons" version="v1" /> and exits with status 0, so the connector emits <Cite name="lost" connectorApi="events" /> with the reason <Cite name="shutdown" connectorApi="lost_reasons" /> and never respawns it. A backend that exits with status 0 without an end event isn't respawned either: the connector emits <Cite name="lost" connectorApi="events" /> with the reason <Cite name="exited" connectorApi="lost_reasons" />.

### Restarts

- Before each restart, the connector waits: <Cite name="respawnBackoff" connectorApi="options" /> before the first, twice the last wait before each one after it, and never longer than <Cite name="respawnBackoffMaximum" connectorApi="options" />. Once a respawned backend has been ready for <Cite name="respawnBackoffReset" connectorApi="options" />, the next wait is <Cite name="respawnBackoff" connectorApi="options" /> again.
- It makes at most <Cite name="respawnLimit" connectorApi="options" /> restarts within any period of <Cite name="respawnWindow" connectorApi="options" />. In place of a restart beyond that limit, it emits <Cite name="lost" connectorApi="events" /> with the reason <Cite name="respawn_limit" connectorApi="lost_reasons" /> and the last exit's status or signal and stderr tail.
- A restart runs the connect sequence as `connect()` does, with the same command, arguments, working directory, environment, endpoint, token and rendezvous file. On loopback with a generated port, the connector first removes the rendezvous file the exited backend left, so that it reads only the new server's port.
- A restart that fails with <Cite name="spawn_failed" connectorApi="errors" />, <Cite name="startup_failed" connectorApi="errors" /> or <Cite name="connect_timeout" connectorApi="errors" /> counts as a restart, and the connector tries again after the next wait. On <Cite name="connect_timeout" connectorApi="errors" />, it first stops the process it started for that restart.
- A restart that fails with any other error, such as <Cite name="verification_failed" connectorApi="errors" />, ends respawning: the connector emits <Cite name="lost" connectorApi="events" /> with the reason <Cite name="unavailable" connectorApi="lost_reasons" /> and that error's code.
- While it respawns, <Cite name="reconnectBudget" connectorApi="options" /> doesn't apply, since the limit bounds the outage.
- While it may still start a backend for an endpoint it generated, the connector keeps the directory it generated for it. It removes the directory once the backend has exited and it won't start another: when respawn is off, has given up, or the app has called `close()`.
- `close()` during a respawn ends it at once, and stops a process the restart started that isn't ready yet.

### Events during a respawn

The backend's exit ends the lease, so the connector has emitted <Cite name="reconnecting" connectorApi="events" />, and unless the app calls `close()`, the respawn ends it with exactly one event:

- A <Cite name="respawned" connectorApi="events" /> event, with the old and new client IDs, once a backend the connector started is ready and it holds a lease on it.
- A <Cite name="reconnected" connectorApi="events" /> event, when another client's backend serves the endpoint instead: one answers the hello before the restart starts a process, or the process the restart started exits with <Cite name="already_running" section="exit_codes" version="v1" /> because another client won the [spawn race](/pipeapi/reference/protocol-v1/#spawn-race). The connector attaches to that backend, and from then on it is an attached client, which never respawns.
- A <Cite name="lost" connectorApi="events" /> event, when the connector gives up.

### Requests and streams during a respawn

- A request not yet sent [waits for ready](#waiting-for-ready) through every restart, until the connector holds a lease or the `Backend` is lost.
- A request in flight when the backend exited is sent again only as [safe retry](#safe-retry) allows, once the connector holds a lease on the new backend.
- An SSE stream [resumes](#server-sent-events) as it would after a reconnect, on a backend that knows nothing of the old one's events unless the app keeps them elsewhere.
- A WebSocket ends, and the connector never opens it again.
- The primitive, and the typed client built on it, keep working, as [addresses](#addresses) says.

### Attached clients during a respawn

A client attached to the backend sees its lease end without an end event, emits <Cite name="reconnecting" connectorApi="events" /> and reconnects. When the respawned backend is ready within the client's <Cite name="reconnectBudget" connectorApi="options" />, the client attaches to it and emits <Cite name="reconnected" connectorApi="events" /> with a new client ID; otherwise it emits <Cite name="lost" connectorApi="events" /> with the reason <Cite name="unavailable" connectorApi="lost_reasons" />. It never emits <Cite name="respawned" connectorApi="events" />. An attached client that should outlast more than the first restart needs a budget longer than the respawning client's waits and the backend's startup together.

### Concurrent respawns

Only the client that spawned a backend's process respawns it, so one exit leads to one respawn at most. A respawn can still race other clients that run `connect()` on the same endpoint with a command of their own. The [spawn race](/pipeapi/reference/protocol-v1/#spawn-race) settles it: one server takes the endpoint, and every other client, the respawning one included, attaches to it.

## A spawned backend's stdio

Standard input, output and error carry nothing of the protocol, as [stdio](/pipeapi/reference/protocol-v1/#stdio) says. When a connector spawns the backend, the app chooses where each stream goes with <Cite name="stdin" connectorApi="options" />, <Cite name="stdout" connectorApi="options" /> and <Cite name="stderr" connectorApi="options" />.

- **stdin** reads the null device by default, so a backend that reads its input, such as with `input()`, gets end-of-file at once rather than waiting forever. `inherit` gives it the client's own input, and `pipe` a stream the `Backend` exposes for the app to write to. The app may also supply a stream of its own.
- **stdout and stderr** go to the connector's log by default: the connector reads each stream and logs each line as a <Cite name="backend_output" connectorApi="log_events" /> record, at the same level for both streams, since uvicorn writes its own informational records to stderr. `discard` reads a stream and drops it, and `inherit` gives the backend the client's own. The app may also supply a sink of its own, such as a callback, a Node `Writable`, a Go `io.Writer`, a .NET `TextWriter` or a file.
- `inherit` suits a console app in development, such as to use `breakpoint()` in the backend. A GUI app has no console to share, and when both processes share a terminal, what the user types may go to either one.

Each connector's issue settles its language's forms: the streams and sinks it accepts, and how the `Backend` exposes a piped stdin.

### Draining

A connector pipes every stream that isn't `inherit`, and it MUST read each one as fast as the backend writes to it, whatever the stream's destination does, so the backend never blocks on a full pipe.

- A destination slower than the backend gets the stream through a queue that holds at most <Cite name="output_queue_maximum" connectorApi="constants" /> of it. While the queue is full, the connector drops what the backend writes, and once it has room again, it logs <Cite name="output_dropped" connectorApi="log_events" /> with how much it dropped.
- To log a stream, the connector splits it into lines at each line feed, removes a carriage return before one, and decodes each line as UTF-8, replacing invalid bytes with U+FFFD. A line longer than <Cite name="output_line_maximum" connectorApi="constants" /> is logged in pieces no longer than that, split between characters. A sink that takes lines gets them the same way, and a sink that takes bytes gets them as the connector reads them.
- When the backend exits, the connector reads each pipe to its end before it reports the exit, but for at most <Cite name="output_end_wait" connectorApi="constants" />, since a process the backend started may hold the pipe open.

### The stderr tail

Unless stderr is `inherit`, the connector keeps the last <Cite name="stderr_tail" connectorApi="constants" /> of what the backend wrote to it, decoded as logged lines are, and drops a partial first line when the kept part holds a whole one. <Cite name="startup_failed" connectorApi="errors" /> and <Cite name="lost" connectorApi="events" /> carry it, so an app can show why its backend failed.

### No console window on Windows

On Windows, a connector MUST start the backend with the `CREATE_NO_WINDOW` creation flag unless one of its streams is `inherit`, so that a console program, such as `python.exe`, opens no console window when a GUI app starts it. Node's `windowsHide` option does this. With `inherit`, the backend shares the client's console instead. Each connector's issue settles how its language sets the flag.

## Logging

A connector logs what it does, so that an app can see how a connection or an outage went. Every connector logs the same events, at the same levels:

<ConnectorApiTable section="log_events" />

- **Levels.** Debug, info, warning and error, each mapped to its language's own, such as Python's `WARNING` or Go's `slog.LevelWarn`.
- **Context.** Every record carries the backend's <Cite name="name" connectorApi="options" />, and once the first lease opens, the client ID of the current lease. A record names its event as the table does, in a structured field where the language's mechanism has them.
- **Silent by default.** A connector logs nothing until the app turns its logging on.
- **Secrets.** As [tokens](/pipeapi/reference/protocol-v1/#tokens) requires, a connector MUST NOT log the token or a session secret, at any level. Nor does it log a header that carries one, <Cite name="X-PipeAPI-Enrollment" version="v1" /> or <Cite name="X-PipeAPI-Session" version="v1" />, a spawned backend's environment or its arguments, or a request's query. The conformance suite's canary case proves it at the most verbose level.
- **Output.** A spawned backend's output goes to a category of its own for each stream, apart from the connector's own records, so the app can route it on its own.

Each connector's issue settles its language's mechanism. Each issue recommends one:

| Language | Mechanism |
| --- | --- |
| Node ([#7](https://github.com/jaARke/pipeapi/issues/7)) | A logger option shaped like `console`, with `util.debuglog` when the app gives none |
| .NET ([#15](https://github.com/jaARke/pipeapi/issues/15)) | An `ILoggerFactory`, through Microsoft.Extensions.Logging.Abstractions, or a delegate with an adapter package |
| Rust ([#16](https://github.com/jaARke/pipeapi/issues/16)) | The `log` facade, behind a default feature |
| Go ([#17](https://github.com/jaARke/pipeapi/issues/17)) | A `*slog.Logger` option |
| Python ([#18](https://github.com/jaARke/pipeapi/issues/18)) | `logging`, with loggers named under `pipeapi` and a `NullHandler` |

## WebSockets

A pipeapi server accepts WebSocket connections, and every connector MUST support them on every transport it supports, through a path its documentation gives: a helper of its own, or a recipe with a WebSocket library over its primitive or `dial()`.

- The opening handshake is an HTTP request, so it carries the headers every request does. A handshake without them gets a [rejection](/pipeapi/reference/protocol-v1/#rejections), which is a plain 403 on an ASGI server without the WebSocket denial response extension.
- A connector's outage handling MUST pass an upgraded connection through untouched: the body of a `101 Switching Protocols` response, which is the connection itself in Go, and the response extensions that hold the upgraded stream in Python's httpcore. A wrapper that buffers or replaces them breaks every WebSocket library built on the primitive.
- Once upgraded, the connection is the app's. The connector never opens it again, and when it drops, the app sees the close or the error its library reports.

Each connector's issue decides whether its language needs a helper:

| Language | Likely path |
| --- | --- |
| Node ([#7](https://github.com/jaARke/pipeapi/issues/7)) | A helper that returns the address and headers to open a WebSocket with, since `ws` replaces a `socketPath` option it's given |
| .NET ([#15](https://github.com/jaARke/pipeapi/issues/15)) | A recipe: `ClientWebSocket` with an `HttpMessageInvoker` built on the connector's handler, on .NET 7 or later |
| Rust ([#16](https://github.com/jaARke/pipeapi/issues/16)) | A helper that builds the handshake request, over `dial()` |
| Go ([#17](https://github.com/jaARke/pipeapi/issues/17)) | A recipe: coder/websocket over the primitive's `*http.Client` |
| Python ([#18](https://github.com/jaARke/pipeapi/issues/18)) | A recipe: httpx-ws over the primitive |

The conformance suite covers each connector on every transport with three cases: an echo round trip that carries the credentials, a handshake without them that the server rejects, and a close from the server that reaches the client.
