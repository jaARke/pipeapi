## Conventions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [BCP 14](https://www.rfc-editor.org/info/bcp14) ([RFC 2119](https://www.rfc-editor.org/rfc/rfc2119), [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174)) when, and only when, they appear in all capitals, as shown here.

The files in <ContractLink path="protocol/v1/" /> are part of this specification. `openapi.yaml` holds the reserved routes, their headers and their bodies; `registry.yaml` holds the names and values an OpenAPI document can't; `rendezvous.schema.json` holds the rendezvous file's shape; and `vectors/` holds the test vectors. The tables on this page and the route pages render those files. Every environment variable, header pipeapi defines, reserved route, constant, rejection code, duration, exit code, feature flag, lease event type, lease end reason and protocol version this page names comes from them, and so does every JSON property name, from `openapi.yaml`'s schemas.

### Terms

- **Backend:** a process that serves an app through the pipeapi server.
- **Server:** the pipeapi server in a backend. Its middleware answers the reserved routes and checks every request before the app sees it.
- **Client:** a program that talks to a backend, whether a pipeapi connector or any other program that implements this specification.
- **Endpoint:** where a backend listens, named by an [endpoint URL](#endpoint-urls).
- **Token:** the secret a client and the server share. Each side proves it holds the token, and the token never crosses the wire.
- **Lease:** a client's lease request, which the server holds open. A backend runs while at least one lease is open.
- **Session:** the client ID and session secret that a lease's first event gives the client, which authenticate its other requests.

### Encodings

- **b64u(n):** n bytes from a cryptographically secure random generator, encoded as base64url ([RFC 4648, section 5](https://www.rfc-editor.org/rfc/rfc4648#section-5)) without padding. An encoder produces the canonical form, in which unused bits are zero, so b64u(32) is 43 characters and the last one's two unused bits are zero. A value that doesn't match the pattern `openapi.yaml` gives it is malformed.
- **Integers in text,** in headers, environment variables and endpoints, are decimal.

## Endpoints

### Endpoint URLs

An endpoint URL names a transport and an address. A client MUST accept exactly these forms, which are case-sensitive, and MUST take everything after the scheme's `://` literally, without percent-decoding.

| Form | Transport | Operating systems |
| --- | --- | --- |
| `unix://<path>` | A Unix domain socket at `<path>` | POSIX |
| `npipe:////./pipe/<name>` | The Windows named pipe `\\.\pipe\<name>` | Windows |
| `tcp://127.0.0.1:<port>` or `tcp://[::1]:<port>` | TCP on the loopback address | All |

- `<path>` MUST be absolute.
- `<name>` MUST NOT be empty or contain `/` or `\`, and the pipe's full path, `\\.\pipe\<name>`, MUST be at most 256 UTF-16 code units, as Windows counts its length.
- `<port>` is an integer from 0 to 65535, without leading zeros. Port 0 marks a [generated](#generated-endpoints) loopback endpoint, whose server reports the port it bound through the [rendezvous file](#rendezvous-file). A client given a port-0 endpoint MUST also be given its rendezvous file's path, and otherwise the endpoint is invalid. Ports 80 and 443 are refused, for the reason [ports 80 and 443](#ports-80-and-443) gives.
- A hostname, a wildcard address or any other address is invalid, as is anything after the port.

A client MUST reject an invalid endpoint before it spawns a backend or connects. A server given an invalid endpoint MUST exit with <Cite name="startup_failure" section="exit_codes" />.

A client MUST also reject, as an unsupported transport, an endpoint whose transport its operating system doesn't support: a `unix://` endpoint on Windows, or an `npipe://` endpoint on POSIX. The connector API names that error <Cite name="unsupported_transport" connectorApi="errors" />. On Windows, a backend listens on a named pipe, since Python's asyncio has no Unix domain socket server there.

### Templates

A client expands templates in a `unix://` endpoint's path and an `npipe://` endpoint's name, so independent clients agree on a shared endpoint, such as `npipe:////./pipe/myapp-{user}`. A `tcp://` endpoint carries none.

- `{user}`: on POSIX, the effective UID. On Windows, the user name that `GetUserNameW` returns, which is the account name without its domain, as Node's `os.userInfo().username` gives it.
- `{session}`: on Windows, the Remote Desktop Services session ID of the client's process, as `ProcessIdToSessionId` gives it. In a `unix://` endpoint, it makes the endpoint invalid, since POSIX has no portable login-session ID.
- `{pid}`: the client's own PID.

A `{` or `}` that isn't part of one of these templates makes the endpoint invalid, and template names are case-sensitive. Expansion is a single pass: the text a template expands to is never expanded again. The rules for [endpoint URLs](#endpoint-urls) apply to the expanded endpoint. A server takes its endpoint as it receives it, already expanded, and expands nothing.

### Generated endpoints

A client given no endpoint generates one, so that no other client knows it:

- **Named pipe:** `npipe:////./pipe/<prefix>-<name>-<uuid>`, or `npipe:////./pipe/<prefix>-<uuid>` for a backend without a name. `<prefix>` is <Cite name="generated_name_prefix" section="constants" />, `<name>` is the backend's <Cite name="name" connectorApi="options" />, which the connector API defines, and `<uuid>` is a random (version 4) UUID in lowercase hyphenated form.
- **Unix domain socket:** `unix://<dir>/<file>`, where `<file>` is <Cite name="socket_file" section="constants" />. `<dir>` is a new directory that the client creates with mode 0700, as `mkdtemp` does, named `<prefix>-` followed by random characters. It sits in `$XDG_RUNTIME_DIR` when that is set and absolute, and otherwise in the system's temporary directory. The socket's path MUST be at most 103 bytes, which is macOS's `sun_path` limit less its terminating NUL, so when it would be longer, the client creates the directory in `/tmp` instead.
- **Loopback:** `tcp://127.0.0.1:0`, with the [rendezvous file](#rendezvous-file) at `<dir>/<file>`, where `<file>` is <Cite name="rendezvous_file" section="constants" />. `<dir>` is a new directory created as a socket's is, which only the user can access: mode 0700 on POSIX, and on Windows an access list that grants only the user, SYSTEM and Administrators, as CPython's mode 0700 does there.

### Rendezvous file

On loopback with a generated port, the server binds port 0, so that the OS picks a free port, then writes that port to the rendezvous file that <Cite name="PIPEAPI_RENDEZVOUS" /> names. The file is a JSON object, encoded as UTF-8, whose shape is <ContractLink path="protocol/v1/rendezvous.schema.json">`rendezvous.schema.json`</ContractLink>. A client ignores a property it doesn't know.

- The server MUST write the file only once it has bound, and atomically: it writes a temporary file in the same directory, then renames it over the file's name.
- The client waits for the file to exist, then reads the port from it. It MUST read the file again before each hello it sends, since a file that a server stopped too abruptly to remove names a port that is no longer that server's, and a new server replaces it.
- The file's directory is always one that a client created for that backend, as [generated endpoints](#generated-endpoints) says. A client MUST NOT give a backend any other rendezvous path: a client given a rendezvous path passes on only one that another client generated.
- The server removes the file as it stops, then the directory if it is then empty, as [generated files](#generated-files) says.

### Transport access

Each transport limits who can reach a backend:

- **Named pipe:** the server MUST create every instance with `PIPE_REJECT_REMOTE_CLIENTS`, so a remote client can't connect over SMB, and with a security descriptor that grants access to the current user only.
- **Unix domain socket:** the socket MUST sit in a directory only its user can access. A generated socket's directory is created so, and a socket path the user gives must sit in such a directory too.
- **Loopback:** the server MUST bind only its endpoint's loopback address, never a wildcard address. The OS still lets every local user connect, so only the token keeps them out (see [limits](#limits)).
- **Rendezvous file:** its directory MUST admit only the user, as a generated rendezvous file's directory does, and a client gives a backend no other [rendezvous path](#rendezvous-file). No other user can then replace the file and point clients at another port.

A client on Windows SHOULD open a named pipe at identification-level impersonation at most, with `SECURITY_SQOS_PRESENT` and `SECURITY_IDENTIFICATION`, so that a rogue pipe server can't act as the client. A client that can't set it is covered under [limits](#limits).

## Environment variables

A client that spawns a backend passes it these variables in its environment.

<RegistryTable version="v1" section="environment_variables" />

- A client MUST pass <Cite name="PIPEAPI_ENDPOINT" /> and <Cite name="PIPEAPI_TOKEN" />, and MUST pass <Cite name="PIPEAPI_RENDEZVOUS" /> exactly when the endpoint is loopback with a generated port. It passes the others only when it has a value for them.
- A spawned backend always receives these names, whatever prefix a client reads its own configuration under.
- The server MUST read these variables at startup and remove them from its own environment, so that the processes it starts don't inherit them.
- A server given a malformed value in one of these variables, an empty token, or a port-0 endpoint without <Cite name="PIPEAPI_RENDEZVOUS" />, MUST exit with <Cite name="startup_failure" section="exit_codes" />.

## Host and proxies

Every request MUST carry the Host header <Cite name="host" section="constants" />, on every transport. The name is never resolved: [RFC 6761](https://www.rfc-editor.org/rfc/rfc6761) keeps `.localhost` names on loopback and out of DNS.

On loopback, the server MUST reject a request whose Host is not exactly that value, without a port, with <Cite name="invalid_host" section="rejections" />, and a request that carries an `Origin` header with <Cite name="origin_forbidden" section="rejections" />. A client always sends that Host and never an `Origin` header, so these checks refuse only requests from elsewhere, such as a web page's. On pipes and sockets, the server MAY skip both checks.

A client MUST NOT send requests to a backend through a proxy: it turns off system proxy settings, proxy environment variables and PAC files for every transport. A proxy receives requests in absolute form, which breaks routing down a pipe or a socket, and whether a proxy's bypass rules exclude a `.localhost` name differs by language and platform.

## Tokens

A backend's clients and its server share one token, which is a non-empty string.

- A client generates a token only with an endpoint it [generates](#generated-endpoints): b64u(32), which carries 256 bits of entropy. A client given an endpoint is given its token too.
- A token the user gives SHOULD carry at least 128 bits of entropy, and comes from configuration the user controls, never from the app's own files, which any process of the same user can read.
- The token never crosses the wire: each side [proves](#proofs) it holds it.
- A client and a server MUST NOT write the token or a session secret to a log, stdout or stderr.
- A client MUST NOT pass the token to a process that runs web content, such as an Electron renderer.

## Connect sequence

A client connects to a backend in these steps, whether or not it spawns the backend. A client that implements the protocol itself, without a connector, MUST follow them too, and hold its lease for as long as it uses the backend.

1. **Resolve the endpoint.** The client [expands](#templates) the endpoint it was given, or [generates](#generated-endpoints) an endpoint and a token.
2. **Attach or spawn.** A client given a port-0 endpoint attaches without spawning, and goes on to step 3: only the client that generated a port-0 endpoint spawns a backend for it. Otherwise the client connects to the endpoint, and attaches to the backend that accepts the connection. When nothing accepts it, because the connection is refused or no such pipe or socket exists, the client starts a backend with its spawn command and the [environment variables](#environment-variables). A client without a spawn command fails instead.
3. **Wait for the hello.** The client requests <Cite name="/__pipeapi/ready" /> with a fresh <Cite name="X-PipeAPI-Nonce" />, and tries again, backing off, until the server answers. On loopback with a rendezvous file, it first waits for the [rendezvous file](#rendezvous-file). The client's deadline bounds the whole sequence, and the client fails when it passes.
   - While a backend the client spawned runs, the client keeps trying. When that backend exits with <Cite name="already_running" section="exit_codes" />, because another server took the endpoint, or exits after answering <Cite name="draining" section="rejections" />, the client keeps trying as one that has spawned nothing. When it exits any other way, the client fails.
   - When the client has spawned nothing, a hello whose connection nothing accepts sends the client back to step 2.
   - A hello answered with <Cite name="draining" section="rejections" /> counts as no answer, as [draining](#draining) says. A hello answered with any other rejection stops the client, since the server isn't one it can verify.
   - A server MUST NOT answer a hello before the app's lifespan startup has run, so a hello means the app is ready.
4. **Negotiate.** The client picks the highest protocol version that both it and the hello's `protocols` list. With none in common, it fails, naming both sides' versions. It reads the rest of the hello by the chosen version's rules, and every later request carries that version in <Cite name="X-PipeAPI-Protocol" /> (see [versioning](#versioning)).
5. **Verify the server.** The client checks the hello's [proof](#hello-proof). Where the client's runtime can read the PID of the process at the other end of the connection, as it can on a named pipe or a Unix domain socket, the client MUST also check that the PID equals the hello's `pid`. On any mismatch, the client MUST NOT enroll with that server. On loopback with a rendezvous file, the file may be stale, so the client reads it again and goes back to step 3; on any other endpoint, it stops.
6. **Enroll.** The client opens its lease, requesting <Cite name="/__pipeapi/lease" /> with <Cite name="X-PipeAPI-Enrollment" />, which answers the hello's challenge (see [enrollment](#enrollment)).
   - A lease request answered with <Cite name="draining" section="rejections" /> sends the client back to step 3, as [draining](#draining) says.
   - One answered with <Cite name="enrollment_failed" section="rejections" />, such as for a challenge that expired or that the server evicted, sends the client back to step 3 once, for a fresh hello. A second one stops the client.
   - One answered with <Cite name="unsupported_protocol" section="rejections" /> stops the client, since the server contradicted its own hello.
7. **Use the session.** The lease's first event, <Cite name="session" section="lease_event_types" />, gives the client its ID and session secret. Every later request carries them in <Cite name="X-PipeAPI-Session" /> (see [sessions](#sessions)), and the backend is ready for the client's requests.

### Spawn race

When clients given the same endpoint spawn backends at the same moment, exactly one server takes the endpoint:

- **Named pipe:** the server creates the pipe's first instance with `FILE_FLAG_FIRST_PIPE_INSTANCE`, which fails when the pipe already exists.
- **Unix domain socket:** the server takes an exclusive advisory lock on the lock file beside the socket, as `flock(2)` takes one, without waiting for it: a server that can't take the lock at once hasn't taken the endpoint. The lock file's path is the socket's with <Cite name="lock_suffix" section="constants" /> appended, and the server creates the file when it is missing. Holding the lock, it removes any socket file a stopped server left at the path, then binds. It holds the lock until it has removed its socket file as it [stops](#stopping), then releases it. A server never removes the lock file, which another server may already hold open.
- **Loopback:** the server binds the port exclusively, with `SO_EXCLUSIVEADDRUSE` on Windows.

The server takes its endpoint before it runs the app's lifespan startup, and accepts connections only once the startup has run. A server that doesn't take the endpoint MUST exit with <Cite name="already_running" section="exit_codes" /> without running the app or serving, and its client keeps trying for the hello of the server that took it, as step 3 says.

A named pipe or a socket settles any race this way, whether its endpoint was generated or given. A port-0 endpoint can't race, since only the client that generated it spawns a backend for it, and binding port 0 never conflicts.

### Enrollment

The hello's `challenge` is single-use and belongs to that hello. The lease request answers it with <Cite name="X-PipeAPI-Enrollment" />: the challenge as the hello gave it, a period, then the [enrollment proof](#enrollment-proof).

- The server MUST accept a challenge at most once, and only within <Cite name="challenge_lifetime" section="durations" /> of the hello that issued it. A lease request that names a challenge uses it up, whether or not the request succeeds.
- The server MUST compare the proof with the one it computes in constant time.
- The server MAY bound how many unused challenges it keeps, evicting the oldest first. A client whose challenge was evicted gets <Cite name="enrollment_failed" section="rejections" />, and tries again as step 6 of the [connect sequence](#connect-sequence) says.
- A lease request whose enrollment is missing, malformed, names a challenge the server didn't issue, already used or let expire, or carries a wrong proof, gets <Cite name="enrollment_failed" section="rejections" />.

### Sessions

The <Cite name="session" section="lease_event_types" /> event gives the client a `client_id` and a `secret`. Every request after enrollment MUST carry <Cite name="X-PipeAPI-Session" />: the client ID, a period, then the secret.

- The server MUST check the session on every request but the hello and the lease request, comparing the secret in constant time. A request whose session is missing or malformed, names an unknown client, carries a wrong secret, or belongs to a lease that has ended, gets <Cite name="invalid_session" section="rejections" />.
- A client ID is bound to its secret, so no client can use another's ID.
- A session lasts as long as its lease. A new lease gets a new client ID, and the server never reuses an ID while it runs.
- Revoking a client ends its lease with an <Cite name="end" section="lease_event_types" /> event whose reason is <Cite name="revoked" section="lease_end_reasons" />, which ends its session. The server's API lets the app revoke one client.

## Proofs

Both proofs are HMAC-SHA256, keyed by the token's text, exactly as given, encoded as UTF-8. The key is never the token trimmed or base64-decoded, so a token of any form works and every implementation keys HMAC the same way. A proof's input is bytes: an ASCII label, one 0x00 byte, then fields of fixed length. Each kind of proof has its own label, so a proof of one kind is never valid as another.

### Hello proof

The hello's `proof` is b64u of the HMAC of these bytes, in order:

| Field | Length in bytes |
| --- | --- |
| The label <Cite name="hello_label" section="constants" />, in ASCII | The label's length |
| 0x00 | 1 |
| The nonce: the bytes the request's <Cite name="X-PipeAPI-Nonce" /> decodes to | 32 |
| The hello's `pid`, as an unsigned big-endian integer | 4 |

The hello's `pid` is the PID of the process that created the endpoint's listener, whether the pipe instance, the socket or the loopback listener, which the OS reports to a client as the connection's peer. A server MUST answer hellos only from that process. The proof binds that PID, so a client that can read its peer's PID detects a proof relayed from another server.

### Enrollment proof

The enrollment proof is b64u of the HMAC of these bytes, in order:

| Field                                                                    | Length in bytes    |
| ------------------------------------------------------------------------ | ------------------ |
| The label <Cite name="enrollment_label" section="constants" />, in ASCII | The label's length |
| 0x00                                                                     | 1                  |
| The challenge: the bytes the hello's `challenge` decodes to              | 32                 |

### Test vectors

The directory <ContractLink path="protocol/v1/vectors/" /> holds test vectors for the hello proof, the enrollment proof and template expansion, in the style of Project Wycheproof: each case is valid or invalid, and an invalid case's flags name the mistake it catches. An implementation SHOULD run them in its tests. Their expected values come from OpenSSL and from these rules, not from any pipeapi code.

## Rejections

When the server refuses a request itself, its response carries <Cite name="X-PipeAPI-Rejected" /> with a rejection code, so a client knows the app never saw the request. A 401 from the server also carries <Cite name="WWW-Authenticate" /> with the scheme <Cite name="auth_scheme" section="constants" /> and the code as its `error` parameter, since [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.2) requires a challenge on every 401. A client MUST tell the server's rejections from the app's responses by <Cite name="X-PipeAPI-Rejected" />, never by the status or the challenge alone: the app's own 401 carries no such header.

<RegistryTable version="v1" section="rejections" />

The server checks a request in this order, and answers with the first check that fails:

1. On loopback, the Host header, then the `Origin` header.
2. The reserved routes' own rules: the route exists and takes the method, and a hello carries a well-formed nonce.
3. On a hello, whether the server is stopping.
4. On every request but the hello, the protocol version.
5. On a lease request, its enrollment; on every other request but the hello, its session.
6. On a lease request, whether the server is stopping.

A WebSocket handshake gets the same rejection as an HTTP request where the ASGI server supports the WebSocket denial response extension, and otherwise a plain 403 without a rejection code.

## Errors

pipeapi adds no error body of its own. A rejection carries its code in <Cite name="X-PipeAPI-Rejected" />, and its body has no shape a client may rely on. Every other response is the app's, unchanged, such as FastAPI's `{"detail": ...}` bodies and its 422 validation errors. Failures outside HTTP, such as no backend at the endpoint, a failed verification or no protocol version in common, are a client's own errors, which the [connector API](/pipeapi/reference/connector-api/#errors) defines, and never HTTP statuses.

## Leases

A lease is a client's request to <Cite name="/__pipeapi/lease" />, which the server holds open and answers with the lease stream. The backend runs while at least one lease is open. The OS closes a connection whose process has died, so a lease can't outlive its client, however the client exits.

- A client holds one lease, from enrollment for as long as it uses the backend, and its [session](#sessions) lasts as long as the lease.
- A client releases its lease by closing the lease request's connection. That ends only its own use of the backend, and never stops a backend whose other clients still hold leases.

### Lease stream

The lease stream is `application/jsonl`: UTF-8 text with one JSON object on each line, and every line ending in LF. Its shape is the `lease_event` schema in the [OpenAPI document](#openapi-document), and every event has a `type`.

- A client MUST ignore an event whose type it doesn't know, and a property it doesn't know.
- The server MUST send each event as soon as it has written it, without holding it in a buffer.

### Lease event types

<RegistryTable version="v1" section="lease_event_types" />

- The server MUST send <Cite name="session" section="lease_event_types" /> first, once, as soon as enrollment succeeds. It carries the client's `client_id` and `secret`, and the lease's TTL in `lease_ttl`: a number of seconds, or null when leases have none.
- While the lease is open, the server MUST send <Cite name="heartbeat" section="lease_event_types" /> every <Cite name="heartbeat_interval" section="durations" />.
- When the server ends a lease itself, it MUST send <Cite name="end" section="lease_event_types" /> last, with the reason, then close the stream. A lease that the client ends, by closing its connection, gets no end event.

### Heartbeats

Heartbeats keep the lease stream from looking idle to a component that drops idle connections. A client MUST NOT apply a read timeout to the lease stream, and MUST NOT conclude that its lease is lost because heartbeats stop: a backend paused in a debugger sends none, yet its leases are open. A lease is lost only when its stream ends, as [lease loss](#lease-loss) says.

### Lease TTL

Leases have no TTL unless <Cite name="PIPEAPI_LEASE_TTL" /> sets one, since a client paused at a breakpoint, or busy with long synchronous work, looks exactly like a client that hangs. With a TTL, the server ends a lease that goes a whole TTL without a renewal, with an end event whose reason is <Cite name="expired" section="lease_end_reasons" />.

- The TTL is at least <Cite name="lease_ttl_minimum" section="durations" />, and the session event gives it to the client.
- Every request that carries the lease's session renews the lease, as the server receives it. A client with nothing else to send renews with <Cite name="/__pipeapi/renew" />, which the server answers with 204.
- A client SHOULD renew at least every third of the TTL, so that a late renewal still arrives in time.

### Lease loss

A client loses its lease when the lease stream ends, whether after an end event or because the connection drops without one. Its session ends with the lease, and the server never gives that client ID again.

- After <Cite name="shutdown" section="lease_end_reasons" /> or <Cite name="revoked" section="lease_end_reasons" />, the client MUST NOT reconnect on its own: the backend is stopping, or the app has refused this client.
- After <Cite name="restart" section="lease_end_reasons" />, <Cite name="expired" section="lease_end_reasons" />, a reason the client doesn't know, or a connection that drops without an end event, the client MAY reconnect.
- To reconnect, a client runs the [connect sequence](#connect-sequence) again from step 1, and enrolls as a new client, with a new ID and session. The connector API says when a connector reconnects, and whether it may then spawn a backend.

## Lifetime

### Graces

The server stops on its own when no client needs it, once a grace has passed:

- **Startup grace:** when no lease has opened within the startup grace after the server starts serving, it stops. It matters only when no client enrolls after the backend starts, such as when the client that spawned it died or failed before enrolling. <Cite name="PIPEAPI_STARTUP_GRACE" /> sets the grace, and its default is <Cite name="startup_grace_default" section="durations" />.
- **Idle grace:** when the last lease ends, the server waits for the idle grace, then stops unless a lease has opened. A grace of 0 stops it at once. <Cite name="PIPEAPI_IDLE_GRACE" /> sets the grace, and its default is <Cite name="idle_grace_default" section="durations" />.

Either grace can be `never`, which is distinct from 0: the server then never stops for that reason, and runs until a shutdown request or a signal stops it, as suits a backend started by hand. No client can attach to a generated endpoint once every client that knows it is gone, so the idle grace defaults to stopping at once. A backend on an endpoint that clients share and come back to is better served by an idle grace of 10 to 60 seconds, so that a client that restarts can reconnect before the backend stops.

### Stopping

The server stops when a client requests <Cite name="/__pipeapi/shutdown" />, when it receives a signal to stop, or when a grace has passed. It MUST stop in this order:

1. It refuses hellos and new leases, as [draining](#draining) says.
2. It sends an end event on every open lease and closes it. The reason is <Cite name="restart" section="lease_end_reasons" /> when the backend is restarting, such as on a reload, and <Cite name="shutdown" section="lease_end_reasons" /> otherwise.
3. It releases the endpoint:
   - On a Unix domain socket, it closes its listener, removes its socket file and releases the lock.
   - On loopback, it closes its listener, and on a generated port removes its rendezvous file, then the file's directory if it is then empty. Connections in TIME_WAIT can hold the port for a while after, so a new server's exclusive bind of a fixed port can still fail then.
   - On a named pipe, it closes every instance that isn't serving a request. The pipe's name stays taken until the server's last instance closes, so the name frees when the requests in flight finish at step 4.
4. It lets the requests in flight finish.
5. It runs the app's lifespan shutdown.
6. It exits with status 0.

Releasing the endpoint before the lifespan shutdown lets a new server take the endpoint while the old one finishes.

Any client that holds an open lease MAY request a shutdown, which stops the backend whatever leases other clients hold. The server answers it with 202, then stops.

### Draining

From the moment the server starts to stop, it answers every hello and every lease request with <Cite name="draining" section="rejections" />, in the order [rejections](#rejections) gives, so that no client verifies or enrolls with a backend that is going away.

A client that gets <Cite name="draining" section="rejections" />, on a hello or a lease request, treats it as no backend having answered yet: it keeps running the [connect sequence](#connect-sequence)'s steps 2 and 3, backing off, until its deadline. Once nothing accepts its connection, it spawns a backend if it may. A backend it spawns that exits with <Cite name="already_running" section="exit_codes" /> makes it try for the hello again, and it may spawn again later, within the same deadline, once nothing accepts its connection.

### Generated files

Each file and directory created for an endpoint has one side that removes it:

- The server removes its socket file as it stops, holding the lock that the [spawn race](#spawn-race) describes. It never removes the lock file, which another server may already hold open, or the socket's directory.
- The server removes the rendezvous file as it stops, then the file's directory only if it is then empty. It removes nothing else there.
- The client that generated a socket's directory or a rendezvous file's directory removes the directory, with anything left in it, once the backend it spawned has exited and it won't start another backend for that endpoint.
- A client that another client gave its generated endpoint, token and rendezvous path, such as an Electron utility process given them by the main process, never removes them.
- When the client that generated a directory exits first, the directory stays until the OS cleans its temporary directory.

## Sharing a backend

A backend serves any number of clients of the same OS user. Clients share a backend by sharing its endpoint and its token, and for a generated loopback endpoint its rendezvous path too. Either the user configures the endpoint and the token for every client, such as an endpoint [template](#templates) and a token from the user's own configuration, or one client passes its generated values to another. On a configured endpoint, every client may carry the spawn command: whichever arrives first starts the backend, and the rest attach, since a [spawn race](#spawn-race) ends with one server. A port-0 endpoint's backend is started only by the client that generated it. The backend runs while any client holds a lease, whichever client started it, and stops after the last lease ends and the idle grace passes.

## Identity

Each lease gives its client an identity, the client ID in the session event, which [sessions](#sessions) bind to a secret.

- **The client** learns its own ID, and nothing about other clients. The ID is opaque to it.
- **The app** learns, through the pipeapi server's API, the client ID of the session each request carries, so it can tell clients apart and send a message to one of them. It learns when each client's lease ends, and it can revoke one client. It never sees the token, a session secret or a proof, since the server removes the headers that carry them.
- The session identifies a client, not the connection, so a client may send requests on any number of connections. Requests from every client reach the same app concurrently, as in any web server.
- A client that reconnects gets a new ID. The server can't tell a client that reconnects from a new one, and after a restart the app's state about the old ID is gone anyway.

## Stdio

Standard input, output and error are not part of the protocol. Neither side interprets anything a backend writes to stdout or stderr: readiness comes only from the hello, and the backend's lifecycle only from the reserved routes. What a connector does with a spawned backend's output is the connector API's to say.

## Versioning

### Discovery and negotiation

A server advertises the protocol versions it speaks in the hello's `protocols`, and the feature flags it supports in its `features`. A client negotiates as the [connect sequence](#connect-sequence) says: it picks the highest version both sides speak, sends it in <Cite name="X-PipeAPI-Protocol" /> on every later request, and fails, naming both sides' versions, when they have none in common. A server that speaks several versions answers each request by the version that header names, and refuses a version it doesn't speak with <Cite name="unsupported_protocol" section="rejections" />.

The hello route, <Cite name="/__pipeapi/ready" />, its <Cite name="X-PipeAPI-Nonce" /> header and the hello's `protocols` are the same in every protocol version, so any client can read any server's versions before it knows which version they share. A client reads the rest of the hello by the rules of the version it picks. A server that speaks several versions answers one hello for all of them, so the hello's body changes across versions only by addition: a later version keeps every property an earlier one defines, with its meaning, and a proof computed another way arrives in a property of its own.

### Compatible changes

Within a protocol version, the protocol changes only by addition: an optional environment variable, header or reserved route, a JSON property, a lease event type, a lease end reason, a rejection code or a feature flag. A change that would break a client or a server built to the version's earlier rules starts a new protocol version instead. So that additions are safe, each side ignores what it doesn't know:

- A server ignores an environment variable, a header or a JSON property it doesn't know.
- A client ignores a header, a JSON property, a feature flag or a lease event type it doesn't know.
- A client treats a lease end reason it doesn't know as a dropped connection, as [lease loss](#lease-loss) says, and a rejection code it doesn't know as it treats any rejection: the server refused the request, and the app never saw it.

### Features

A feature flag names a capability that a server adds within a protocol version. A client uses a flagged capability only when the hello's `features` lists the flag, and otherwise works as the version's own rules say. A server MUST NOT require a client to use a feature.

## Security considerations

### Trust boundary

The trust boundary is the current OS user. The protocol keeps out the network, other users and web content. It doesn't defend against a malicious process that runs unsandboxed as the same user, which can read the client's and the server's memory, environment and files, so no secret pipeapi holds is safe from it. Against processes of the same user, the protocol only limits accidents, such as a buggy or confused client, and keeps a leak small. The table says which group each mitigation targets, and claims no more.

### Threats

| Threat | Mitigation | Sections |
| --- | --- | --- |
| The network reaching the backend | A named pipe refuses remote clients, and a Unix domain socket has no network address. A loopback backend binds a loopback address only, never a wildcard address. | [Transport access](#transport-access), [endpoint URLs](#endpoint-urls) |
| Another local user connecting | A named pipe admits the current user only, and a Unix domain socket sits in a directory only the user can access. On loopback any local user can connect, and only the token keeps them out. | [Transport access](#transport-access), [limits](#limits) |
| Another process of the same user connecting by accident | A generated endpoint is unguessable, or the user configures one. A client enrolls against the token, and every request carries a session. | [Generated endpoints](#generated-endpoints), [enrollment](#enrollment), [sessions](#sessions) |
| A process taking the endpoint first | A server creates a pipe's first instance, holds the lock file beside a socket, or binds a port exclusively, and exits when it can't. A process of the same user can still add pipe instances afterward. | [Spawn race](#spawn-race), [limits](#limits) |
| A rogue pipe server acting as the client | A client opens a pipe at identification-level impersonation at most, where it can. | [Transport access](#transport-access), [limits](#limits) |

| The token leaking to web content | A client never passes the token to a process that runs web content. | [Tokens](#tokens) |
| A token stored with the app | A token the user gives comes from configuration the user controls, never from the app's own files. | [Tokens](#tokens) |
| A web page reaching a loopback backend, directly or through DNS rebinding | The Host header must be exactly the fixed value without a port, and a browser sends that only to ports 80 and 443, which endpoints refuse. | A squatter collecting the token, or relaying a client's hello to the real server | The token never crosses the wire, and a client checks the hello's proof before it enrolls. Where a client can read the server's PID, it checks the PID the proof covers, which detects a relay. | [Connect sequence](#connect-sequence), [hello proof](#hello-proof) |
| A rendezvous file pointing clients at another port | The file's directory admits only the user, and a client enrolls only with a server whose hello proves it holds the token. | [Transport access](#transport-access), [connect sequence](#connect-sequence) |

### Ports 80 and 443

On loopback, the Host check rests on a browser's habit of adding the port to the Host header for any port but its scheme's default. [RFC 6761](https://www.rfc-editor.org/rfc/rfc6761#section-6.3) lets a resolver, a browser's included, answer any `.localhost` name with a loopback address, so on port 80 or 443 a web page's request could carry a Host header exactly like a client's, and the check couldn't tell them apart. Refusing both ports keeps the check sound, and the `Origin` check and the session remain behind it.

### Limits

The protocol can't defend against these:

- **A malicious process of the same user,** running unsandboxed. It can read the token from either process's memory or original environment block, read the user's files, and add instances to a named pipe after the server created the first one, so that a client may connect to its instance rather than the server's.
- **Other users on loopback.** Any local user, in any session, can reach a loopback port, and only the token keeps them out. Machines with several users' sessions, such as Windows terminal servers, and deployments that a security review covers SHOULD use a named pipe or a Unix domain socket instead.
- **A relayed hello where a client can't read its peer's PID.** On loopback, and on any transport whose runtime doesn't give the client its peer's PID, a client can't detect a proof relayed from another server.
- **A pipe opened without identification-level impersonation.** A client that can't set it leaves a rogue pipe server, which only a process of the same user can create, able to act as the client.
- **Name collisions and squatting on configured endpoints.** On Windows, `{user}` expands alike for accounts of the same name in different domains, so their endpoints collide. Any local user can create a configured pipe name or bind a configured loopback port first, which makes the server exit with <Cite name="already_running" section="exit_codes" /> and its clients time out. Generated endpoints avoid both.
- **Sandboxed clients.** A client sandboxed by the OS, such as in an AppContainer or at low integrity, can open a named pipe only when its security descriptor grants the sandbox access explicitly, which the protocol doesn't.
